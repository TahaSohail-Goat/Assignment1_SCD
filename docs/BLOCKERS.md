### B-009 — branch model (resolved 2026-09-25)

| Fact | Detail |
|---|---|
| Assignment wording | "Two branches: dev for work, main for deployable software" (§3.4); `ci.yml` "on pull request to main, **on push to dev**" (§3.4); rubric A2 "Two-branch model with dev plus feature branches" (§4). |
| Pack wording | `docs/GITHUB_WORKFLOW.md`: "`dev/<issue-number>-<slug>` — developer integration branch for the specific issue … the branch named by the assignment's dev/feature workflow". |
| Technical constraint | Git stores branches as files under `refs/heads/`. A branch called `dev` is a *file*; `dev/1-foo` needs `dev` to be a *directory*. They cannot coexist. |
| Option 1 — pack convention only | Branches `dev/<n>-<slug>` → PR → `main`. `ci.yml` triggers `push: branches: ['dev/**']`. No branch literally named `dev`. Least overhead. Risk: a marker looking for a branch named `dev` (rubric A2, 2 marks). |
| Option 2 — literal `dev` + feature branches | Long-lived `dev`; short-lived `feature/<n>-<slug>` (or `feat/`); feature → `dev` PRs, `dev` → `main` PRs. Matches the assignment text exactly. Needs edits to `GITHUB_WORKFLOW.md`, `PROMPT.md`, `CLAUDE.md`/`AGENTS.md` references and one extra PR per integration. |
| Recommendation (accepted) | **Option 2**: the assignment uses `dev` as a branch name in two places and `ci.yml` "on push to dev" is only meaningful with a branch called `dev`. Renaming today costs one branch; it costs more with every later PR. Decision and doc edits should happen before PR #2 is opened. |
| Outcome | Owner chose Option 2 on 2026-09-25 after PR #9 (which used `dev/1-phase-00-baseline`) had been rebase-merged. Because that branch would have blocked creating `dev`, it was deleted (tree identical to `main`, last commit `000d3de`, still reachable through the PR) and `dev` was created from `main` (`349fe86`). Issue #10 carries the documentation changes: `PROMPT.md`, `AGENTS.md`, `docs/GITHUB_WORKFLOW.md`, `docs/PHASE_EXECUTION_PROTOCOL.md`, `docs/CICD.md`, the PR template. |

### B-010 / B-011 — partner and branch protection

GitHub does not allow a PR author to approve their own PR, so "≥ 1 approval" cannot be satisfied by a single account. Until the partner is a collaborator: keep working through PRs, **do not merge**, and do not enable "require approvals". After the partner joins and CI exists, enable protection (require PR, require ≥ 1 approval, require status checks, block force-push and deletion), then take the evidence screenshot for `docs/evidence/`.
